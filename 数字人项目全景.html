01 / POSITION

先划边界：基础 Harness 与数字人 Harness

基础 Harness 解决“一个 Agent 怎么循环、怎么调工具”；数字人 Harness 解决“一个绑定真人的 Agent 怎么持续工作”。

Base Harness

通用 Agent 循环

一个 AgentLoop，加上文件、bash、web、todo、plan、subagent、MCP 等通用工具；上下文靠 compaction 控制，记忆靠通用 memory core。

AgentLoop builtin tools todo / plan compaction MCP
Digital Human Harness

绑定真人的领域运行时

在基础循环外面，接上工作对象、账号身份、跨账号 Broker、SOP 能力、记忆治理、审批与沙箱。这不是换一个 ReAct，而是在宿主上长出一层领域 Harness。

work runtime Broker SOP owner memory approval
一句话：基础 Harness 是“Agent 怎么想、怎么调工具”；数字人 Harness 是“谁在工作、工作怎么流转、跨账号怎么协作、能力从哪来、状态和记忆放在哪”。
02 / PRODUCT OBJECTS

产品对象：数字分身、数字员工与 owner

不是“一个更长的 Prompt”，而是有稳定身份、账户归属、工作区和权限边界的对象。

数字分身 / Personal Agent

绑定真人 owner，围绕本人工作环境持续学习与迭代；跨会话、跨项目理解上下文并统筹工作。能力覆盖用户本人可在产品中完成的操作：查询、调用工具、私聊、建群、协作。

owner 绑定稳定对象 ID账户私有数据

数字员工 / Expert Agent

承载可复用的专业能力或企业流程，不必绑定真人。与数字分身共享底层知识、SOP、Skill、执行与协作能力，但身份、所有权和使用范围分别建模。

可复用能力不必绑定真人企业流程
03 / PRODUCT CHAIN

工作怎么进来、怎么被接住、怎么交付

产品层是三类 Agent；任务记录是三者唯一共享的协作载体。

角色输入输出明确不做
发现 Agent追踪目标 + 授权来源新任务，或与原任务的关联不执行、不找人、不建群、不发协作消息
调度 Agent本人 / 外部交办、查询、调整任务记录、执行绑定、进展回复不做具体业务、不组织协作
执行 Agent任务与要求成果、任务更新、交付回执不直接唤醒调度 Agent，靠任务更新触发通知
04 / TECHNICAL ROLES

技术层四角色：Discovery / Manager / Coordinator / Executor

产品语言里的“调度”在技术上收成了统一 Manager；Coordinator 只在授权的 TeamRun 内存在。

DISCOVERY
发现 / 研究
做什么
高召回扫描授权来源，再按缺口定向调查，提交 ResearchReport。
不做什么
不接收正式工作，不创建执行节点。
关键词
ResearchReport · 证据 · 覆盖 · 未知 · 关系建议
MANAGER
统一 Manager
做什么
所有任务入口汇入同一个逻辑 Manager；评估、接收、关联、暂缓或拒绝，维护目标、计划、依赖与验收。
不做什么
不亲自承担耗时执行；不直接修改持久化状态。
关键词
ManagerRun · 接纳 ≠ 派发 · 最终验收
COORDINATOR
协作协调
做什么
只在 Manager 发起且授权的 TeamRun 内组织成员、拆分 WorkUnit、跟进、局部验收与汇总。
不做什么
不接管 WorkCase 总体目标、接收决策和最终验收。
关键词
TeamRun · 不嵌套 · 单 Coordinator
EXECUTOR
执行
做什么
只执行明确的 ExecutionSpec，返回 Result、Need、证据或产物。
不做什么
不扩目标、不接收新的业务任务、不能给自己派活。
关键词
ExecutionSpec · Result / Need · 有界运行
一个 owner 只有一个逻辑 Manager。 owner、external_conversation、team_member 是同一个 Manager 在不同入口和授权范围内的运行，不是三个 Manager 实例。RunContext 由 Runtime 生成，消息正文或 Prompt 不能扩大它。
05 / WORK OBJECTS

任务与运行解耦：WorkCase 不跟 Session 走

长寿命的业务工作，与短寿命的一次运行分开；失败、超时、结束都不能直接等于任务失败。

业务状态

WorkCandidate / WorkCase / WorkNode：这件工作进行到哪一步。等待、暂停、失败、取消都有明确标记。

执行状态

AgentRun：某次模型或工具运行正在做什么。结束、失败、超时都不等于任务完成。

审计状态

Event / Trace / Policy Audit：为什么变化、具体做了什么、依据什么策略放行。

06 / RESPONSIBILITY

协作与责任：接纳 ≠ 派发，提交 ≠ 完成

架构里最难的不是让 Agent 干活，而是谁接纳、谁派发、谁验收、谁最终负责。

协作的三种方式

独立完成：直接使用工具、知识与 Skill。私聊 / 直接调用：检查权限后提交子任务、追问、接收结果。群聊协作：创建或复用群，按 owner 策略邀请分身/员工，真人由用户手动添加。

协作子 Agent 的边界

一轮只绑定一个群、一个目标。允许读取绑定群消息、提问、澄清、向父执行 Agent 提交结果；禁止找人、拉群、换群、私聊、创建其他协作任务或子 Agent。

07 / CONTROL PLANE

存算分离：Broker 协作日志与群级存储

Broker 保存身份、目录、授权引用、协作消息日志、每目标 inbox/队列和回执，并唤醒目标 Manager；群级协作存储保存黑板与文件快照；私有知识、记忆、凭据、沙箱、执行上下文留在 owner。

口径：当前实现是 Broker 协作日志/队列 + 群级存储 + owner 执行环境；r266 的 holder / sidecar 是把 Runtime 搬到云端的演进方向。
08 / EVENT-DRIVEN

事件驱动与恢复：一次 ReAct 只是一次有界运行

事件进入、Scheduler 唤醒、AgentRun 执行、结果回写、事件再驱动；等待不是失败，恢复不是重跑。

10 / REACT

标准 ReAct 的 Plan / Tool / Memory

一次 ReAct 是一个 AgentRun；Plan 锚定验收，Tool 带治理，Memory 共享但隔离。

Plan

Host：todo_write 是会话级 checklist，不是最终计划；enter_plan_mode / exit_plan_mode 是计划模式。

数字人：计划锚定 WorkCase 的目标、约束、验收标准；写清下一步、等待项、停止条件；新信息到达后重规划。

计划跨 AgentRun 存活；一次运行结束不等于任务结束。

Tool

基础：文件、bash、web、todo、plan、skill、subagent、MCP、用户交互。

数字人：SOP 工具、跨账号会话工具、owner 读取、工作扫描/执行/交付。

工具契约带授权、风险确认、审计、真实回执；授权可以按 run 作用域。

Memory

层：系统提示词概览、关键词详情、长期记忆、项目记忆、工作记忆、任务记录、会话上下文。

写回：结果先形成 MemoryCandidate，带证据、范围、置信度，由记忆机制或 owner 策略审核。

三个 Agent 共享知识/记忆，但各自上下文独立。

11 / CAPABILITY SUPPLY

SOP：经验怎样变成可执行能力

SOP 是架构里的一段“能力供给”，不是架构中心；结构合法、能力可用、业务执行正确是三件不同的事。

持久 SOP 工具

run_sop 立即返回 runId，之后用 sop_wait / sop_status / sop_result / sop_cancel / sop_retry 查询和控制。长流程不靠一个阻塞调用硬等。

生命周期

知识包携带已发布的文本与 Graph；本地留草稿；更新成对确认、成对发布；在途任务保留原版本绑定。知识变了，流程版本怎么办，有明确答案。

共通点

都把任务和运行分开；都强调不可变记录、幂等、授权固化和故障恢复；都不希望人盯着每个会话。

关键差异

13 / RESUME THREADS

四条简历主线：产品 → 协作 → 分工 → 稳定性

01 / PRODUCT

产品与知识供给

02 / COLLABORATION

事件唤醒与状态流转

群聊、外部请求、定时扫描以事件唤醒 Agent；单次 AgentRun 无状态，长周期任务通过任务记录在多次运行间流转，等待、恢复、验收都落到状态上。

事件唤醒无状态 AgentRun长周期状态流转
03 / DIVISION

多 Agent 分工与协作

Discovery 找线索，Manager 接纳、规划与验收，Coordinator 组织 TeamRun，Executor 执行明确任务；群聊协作通过共享黑板同步目标、分工、依赖和结论，明确接纳 ≠ 派发、提交 ≠ 完成。

多 Agent职责边界共享黑板协作
04 / STABILITY

稳定性与存算分离

远端 Broker 保存跨账号消息、队列和回执，作为恢复依据；本地 Runtime / owner 负责计算、私有知识、记忆、凭据和执行环境；进程重启后按 operationId 恢复，不重跑副作用。

远端 Broker本地 Runtime存算分离恢复
叙事顺序：产品是什么 → 用户怎么协作 → 内部怎么分工 → 怎么保证稳定。扫描/蒸馏/分身放第 1 点，事件唤醒与状态流转放第 2 点，Agent 职责与黑板放第 3 点，远端 Broker 与本地 Runtime/owner 放第 4 点。
