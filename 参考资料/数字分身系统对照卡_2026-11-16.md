# 数字分身系统 × DeepSeek Super-agent 对照卡

> **性质**：本地制作的技术映射卡，2026-11-16。不是外部文章，也不是“逐项等价”或“已上线”的声明。
> **用途**：回答“你们和 DeepSeek 一样吗”、准备简历第 2–4 点和面试追问。
> **配图**：已从公开仓库中移除（版权/体积原因），以下保留文字对照。



## 对照表

| # | DeepSeek 核心概念 | 数字分身系统对应设计 | 解决的问题 / 底层机制 |
| ---: | --- | --- | --- |
| 1 | 调度入口 Router | **Manager 管理 Agent**：统一入口 · 工作管理 · 最终验收 | 承接交办与跨工作管理；保留目标和验收，具体工作交给执行侧 |
| 2 | 执行单元 Worker | **Executor 执行 Agent**：ExecutionSpec · 工具 · 工作区 | 独立上下文与受限能力；按明确规格完成工作，返回 Result 或 Need |
| 3 | 触发事件与发现 Trigger / Event Filtering | **Runtime 准入 + Discovery**：代码过滤 · 线索发现 · 定向补查 | 先核验来源、身份与范围；发现 Agent 提交证据，Manager 决定是否接纳 |
| 4 | 任务上下文线 Thread / Subscription | **群 / 私聊上下文与任务绑定**：Thread · WorkCase / TeamTask | 后续消息继续原工作；上下文可多方订阅，订阅不会新增权限 |
| 5 | 任务内团队协作 Worker / Agent Team | **Coordinator 协调 Agent**：按需 TeamRun · 分工与汇总 | 在 Manager 之下组织协作；跨分身经目标入口请求，不调派对方 Manager |
| 6 | 工作与执行绑定 Ticket / Assignment | **WorkCase / WorkNode**：执行绑定与 AgentRun 分层记录 | 工作、派发、运行分别保存；换执行器或会话，仍延续原任务和已完成事实 |
| 7 | 全双工交互 Full-duplex | **前台 Manager 持续接话**：后台执行 · 作业标识 · 事件回投 | 耗时操作启动后即返回；前台可接收查询与调整，结果作为新事件回投 |
| 8 | 计算、状态、环境分离 | **Agent 计算与调度**：状态存储 + 本地/远端执行环境 | 推理、状态、环境分别管理；执行环境恢复后，核实已有进度再继续 |
| 9 | 上下文缓存 Inline / Spill / Recall | **最小 Scope Projection**：摘要与引用 · 获准背景按需加载 | 只装配当前任务所需信息；长历史和产物保留引用，需要时再补读 |
| 10 | 版本化授权 Policy / Mandate | **Runtime 权限与策略校验**：授权依据 · policyVersion · revision | 接单依据与授权版本留痕；受限动作逐项校验，消息正文不能扩大权限 |
| 11 | 持久化与故障恢复 Journal / Outbox / Retry | **Event Journal + 快照 + Outbox**：幂等提交 · 可恢复派发 · 回执核对 | 结果先保存，再可靠通知；重启可恢复，投递可重试，未知回执先核实再处理 |
| 12 | 独立监督 Watchdog | **运行监测 + 管理验收**：独立语义 Watchdog 待评估 | 确定性故障与业务偏离分开；当前监测与验收机制，不等同独立语义监督 |

## 逐行解释

| # | 怎么理解 | 边界，不要说过头 |
| ---: | --- | --- |
| 1 | Router 只负责“分派”；Manager 还负责目标、计划、依赖和最终验收。所以 Manager 比 Router 宽，不是同义词。 | 不要说“Manager 就是 Router”；Manager 的职责包含验收，Router 通常不验收。 |
| 2 | Executor 收到的是明确 ExecutionSpec，能力受 scope 限制，返回 Result / Need；它不是“什么都能干的 Worker”。 | 不要写成“Executor 拥有完整工具和无限权限”；受限能力是设计的一部分。 |
| 3 | 事件先由代码做来源、身份、范围过滤；Discovery 做线索发现和定向补查；Manager 决定是否接纳。 | 不是“所有事件都让大模型判断”；代码过滤在前，模型判断在后。 |
| 4 | 群聊/私聊的上下文绑定到 WorkCase / TeamTask；同一任务线的后续消息回到原工作；多方可以订阅同一上下文。 | **订阅不新增权限**；不要把“能收到消息”写成“能执行动作”。 |
| 5 | Coordinator 只在 Manager 授权的 TeamRun 内做分工和汇总；跨分身要经目标入口请求，由对方 Manager 承接。 | 不要写“Coordinator 可以直接调派对方 Manager 或 Executor”；跨账号必须经过目标 Manager。 |
| 6 | WorkCase 是业务工作，WorkNode 是工作图节点，AgentRun 是一次运行；换执行器或会话，任务和已完成事实仍然保留。 | Ticket/Assignment 不直接等同 WorkCase/AgentRun；这是职责映射，不是对象一一对应。 |
| 7 | 前台 Manager 保持可接话，耗时操作转后台；完成后以事件回投，前台可以继续查询和调整。 | 档案里没有找到 `start()` / `stop()` 全双工实现；这是设计映射，不写“已实现全双工”。 |
| 8 | 推理、状态、执行环境分开管理；环境恢复后先核实已有进度，再继续。 | 不要写“实现了云端 Agent Loop + 端侧 daemon”；你们的落地形态是 Broker 控制面 + owner 执行环境。 |
| 9 | 只给当前任务需要的上下文；长历史和产物用摘要/引用，需要时再补读。 | 不是“上下文越大越好”；Scope Projection 的目标是少而准。 |
| 10 | 授权要带依据和版本；每个受限动作逐项校验；消息正文不能扩大权限。 | 不要写“有 Prompt 约束就够了”；权限在 Runtime，不在提示词。 |
| 11 | 结果先落库，再可靠通知；派发可重试、幂等；回执未知时先核实，不重复副作用。 | 不要写“失败就重试”；未知回执要先核对原 operationId。 |
| 12 | 当前有运行监测和管理验收；独立语义 Watchdog 仍是待评估项。 | 不要把“运行监测 + 管理验收”写成“已有独立 Watchdog”。 |

## 卡底的三句话

- **内部委派**：Manager → Coordinator → Executor；独立任务可由 Manager → Executor。
- **跨分身协作**：Coordinator 向目标入口提交请求，由对方 Manager 自主承接。
- **说明**：按职责与机制建立对应，非逐项等价或已上线声明；Manager 的职责比纯 Router 更宽；Ticket / Assignment 不直接等同 WorkCase / AgentRun；独立语义 Watchdog 暂列待评估。

## 面试怎么用

- 被问“你们和 DeepSeek 一样吗”：先承认同构——都在解决长期任务、上下文、授权、恢复；再讲差异——Manager 比 Router 多最终验收，WorkCase/AgentRun 比 Ticket/Assignment 多一层业务/运行分离，跨账号必须经过目标 Manager。
- 被问“有什么创新”：讲分层可见性（对外的数字分身成员身份 + 对内的子 Agent 收敛）、owner 身份与验收语义、Broker 控制面 + owner 执行环境。
- 不要逐项说“我们也有”：卡上标了“待评估”的 Watchdog、没有实现证据的全双工，都不要写成已完成。
